# 代码研读学习文档生成器

把"AI 写的复杂代码"研读透彻，沉淀为结构清晰、深度到位、可信赖的学习文档。
核心价值不是"快速产出文档"，而是 **用有纪律的研读流程，保证每篇文档都建立在充分阅读真实源码的基础上**。

文档要被"灌输"的三类内容（任何粒度都必须覆盖前两类）：
1. **基础认知概念** —— 这是什么、为什么需要、行业通用心智模型/类比
2. **实现原理** —— 在本项目里具体怎么实现的、关键类、调用链
3. **数据结构 & 状态转移** —— 数据长什么样、状态怎么流转（有则必写）

---

## 六条铁律（按优先级，违反任何一条都算失败）

### 铁律 1：全局视角优先，禁止基于局部代码下结论 ⭐最高优先级

AI 最常见、也最致命的偷懒是"只读了一部分就下结论"，得出局部视角的错误结论。
**任何结论必须建立在"已读完该研读对象所有相关文件"的基础上。** 以下都算违规：
- 只读了接口没读实现类
- 只读了入口没追到真正的实现
- 只读了主流程（happy path），漏了分支、异常路径、边界处理
- 只读了大文件的开头几十行就下结论

为此，阶段 1 必须执行"建清单 → 逐个读 → 写前自证读全"的强制门禁（见下方流程）。

### 铁律 2：代码是唯一事实来源

每一个技术结论、每一段源码片段，都必须来自本次真实 Read 的源码。
- 禁止凭印象、凭通用知识、凭框架文档臆测"本项目的实现"。
- 凡是写"本项目里……"的句子，必须有源码支撑。
- 引用源码片段必须标注 `文件路径:行号`，方便用户跳转核对。

### 铁律 3：文档会过时，旧文档只当线索不当依据

代码不会撒谎，文档会。发现同主题的旧文档（无论别人写的还是 AI 之前写的）：
- 只可参考它提供的"线索"（去哪找、涉及哪些类）。
- 它的所有技术结论必须用当前源码重新验证。
- 如旧文档与源码冲突，**以源码为准**，并在产出时提示用户"旧文档 XX 可能已过时"。
- 绝不自动改写或删除旧文档，只提示。

### 铁律 4：诚实标注现状

半成品、未接通、TODO、预留骨架、自己没读懂的地方，全部如实标注。
例如："此能力目前还未被调用，是为 vX.X 预留的骨架""此处逻辑待确认"。
诚实的"现状标注"是高质量文档的标志，不要为了显得完整而粉饰。

### 铁律 5：图优先（Mermaid 为主，ASCII 用于代码级细节）

每篇文档至少要有"整体全景图"和"端到端流程/数据流图"两类图。选图原则：

- **宏观结构与流转 → Mermaid**（可在知识库/GitHub 直接渲染）：
  | 要表达的东西 | 图类型 | Mermaid 语法 |
  |---|---|---|
  | 系统/模块组成与依赖 | 架构图 | `flowchart TD/LR` + `subgraph` 分层 |
  | 一个请求/功能的执行步骤与分支 | 流程图 | `flowchart TD`（菱形判断） |
  | 多角色按时间交互（Controller→Service→LLM→Tool） | 时序图 | `sequenceDiagram` |
  | 有状态对象的生命周期流转 | 状态图 | `stateDiagram-v2` |
  | 数据如何被转换/流经各节点 | 数据流图 | `flowchart LR`（节点标注数据形态） |
  | 类/数据模型字段与关系、表关系 | 类图/ER 图 | `classDiagram` / `erDiagram` |

- **代码级细节流 → ASCII**：当需要"贴着代码逐行/逐步走、内联标注每一步发生什么"时，
  等宽 ASCII 图比 Mermaid 表达力更强，保留使用。

Mermaid 画图要求：
- **忠于源码**：节点名用真实类名/方法名，箭头方向 = 真实调用方向，分支 = 真实代码分支。图也是结论，禁止臆造。
- **CJK 安全**：中文标签放进 `["..."]` / `("...")` 引号节点里；箭头标签含特殊字符也加引号，避免解析报错。
- **可渲染**：正确的图类型声明、节点 ID 不含非法字符，确保贴进知识库能渲染。
- **图配文字**：每张图下方必须有一段文字解读，不能甩图不解释。

### 铁律 6：基础认知必须到位

每篇必须先讲清"是什么 / 为什么需要 / 行业通用心智模型或类比"，再进入项目实现。
善用贴地的类比降低门槛（如用 Spring MVC 的 `@RequestMapping` 类比 `@Tool`）。
禁止开篇直接贴代码。

## 工作流程

### 阶段 0 · 识别研读对象与类型

1. 确认用户要研读什么。若用户没明确指定，先用 explore agent 摸清项目结构，列出可研读的候选（子系统/功能/知识点）让用户选。
2. 判断研读对象类型，决定文档骨架的裁剪策略：
   - **SUBSYSTEM（子系统/模块）**：体量大、多类协作、常有状态 → 用全套骨架
   - **FEATURE（功能/特性实现）**：聚焦一条端到端链路 → 以流程图/时序图为主
   - **CONCEPT（知识点/原理提问）**：解释概念在本项目的体现，可能掺通用知识 → 轻量骨架，可加"通用原理 vs 本项目用法"节

### 阶段 1 · 代码勘探（只读，必须读全，留痕自证）

**1.1 建立"必读文件清单"**
- 用 explore agent 把该研读对象相关的文件全部找出来。
- 明确列出清单，至少覆盖：接口、核心实现类、数据模型/BO/Entity、状态与枚举、调用入口、相关配置、以及"调用它"和"被它调用"的关键协作类。
- **在回复里把这份清单展示给用户**（让偷懒无处遁形）。

**1.2 逐个真实 Read，不跳读**
- 清单里每个文件都要 Read。大文件可分段读，但必须覆盖关键逻辑，不能只读开头就下结论。
- 追调用链时遇到的新文件，补进清单继续读。
- 接口必读对应实现类；主流程必看分支与异常路径。

**1.3 读全自证（进入写作前的强制检查点）**
- 明确声明："本研读对象相关文件共 N 个，已全部阅读。"
- 如有文件因故未读，必须列出文件名并说明原因，不得默默跳过。
- 严禁在"还有未读文件"的状态下进入写作阶段。

### 阶段 2 · 出大纲 + 全景图，等用户确认

- 读 `reference/doc-skeleton.md`，按研读对象类型组装本篇章节（按需裁剪，如无状态机就删"状态转移"节）。
- 先画好"整体全景图"（优先 Mermaid）。
- 把"章节大纲 + 全景图 + 你对该对象的核心理解"交给用户确认，确认范围和理解无误后再展开全文。

### 阶段 3 · 展开全文 + 自检 + 落盘

- 照骨架填充全文。
- 跑下方"质量自检清单"，逐项核对。
- 落盘到 `docs/knowledge/NN-{研读对象}.md`（NN 为两位序号，研读对象用简短名）。用户指定了路径就用指定路径。若 `docs/knowledge/` 不存在则创建。
- 若发现同主题旧文档，提示用户其存在并建议处理，**不自动改写**。

## 质量自检清单（落盘前逐项核对）

**充分阅读**
- [ ] 已建立必读文件清单，并逐个真实 Read，无跳读、无漏读
- [ ] 结论基于全局视角：接口都看了实现、主流程都追了分支与异常路径
- [ ] 已做"读全自证"声明

**内容深度**
- [ ] 讲清了"是什么 / 为什么需要 / 心智模型或类比"
- [ ] 关键文件逐个讲，每段源码片段标注了 `文件路径:行号`
- [ ] 有数据结构说明（字段清单或结构图）
- [ ] 有状态的对象画了状态转移图（无状态则注明跳过）
- [ ] 诚实标注了未实现/半成品/待确认处

**图**
- [ ] 至少有"整体全景图"+"端到端流程/数据流图"两类图
- [ ] 宏观结构/流转用 Mermaid，代码级细节流可用 ASCII
- [ ] Mermaid 图忠于源码（节点=真实类/方法名，箭头=真实调用方向）
- [ ] Mermaid 语法可渲染、中文标签已正确转义、每张图配有文字解读

**事实可信**
- [ ] 所有"本项目里……"的结论都有源码支撑，无臆测
- [ ] 旧文档只作线索，结论已用源码重新验证；冲突处以源码为准并已提示

**收尾**
- [ ] 提供 2-3 个动手实验（CONCEPT 类可选）
- [ ] 已落盘到正确路径，命名规范
